# Testing

This document says what the team tests and why.

## 1. What we test and why

All tests live in `backend/tests` (pytest) and `frontend/tests` (node:test). There is no browser automation: the interface is checked by render tests and by the browser acceptance checklist in `docs/ui.md`; unrecorded checks remain pending.

| Layer | Code | Test kind | Where |
|-------|------|-----------|-------|
| Services and domain logic | `scoring.py` (rules, `has_history`), `scoring_service.py` (BR1, BR4, BR5, BR6 order), `privacy.py` (masking and encryption) | Unit tests that call the functions directly, including threshold boundaries, golden cases that pin exact scores and reasons, and the BR5 window with a fixed clock at the one-hour cutoff | `test_scoring_unit.py`, `test_scoring_rules.py`, `test_br5_window.py`, `test_scoring_golden.py`, `test_privacy.py` |
| Repository and database | SQLAlchemy models, constraints, migration, seed | Integration tests on an in-memory SQLite database created fresh for each test. No separate repository class exists, so this layer is tested through the models, the migration and the seed | `test_models.py`, `test_br_integrity.py`, `test_migration.py`, `test_walking_skeleton.py` |
| API routes | FastAPI routers for auth, users, loan applications, scoring, dashboard, approval | Integration tests through FastAPI `TestClient` with the same in-memory SQLite, covering status codes, error messages, access control and that nothing is saved after a 422 | `test_auth.py`, `test_applications.py`, `test_application_validation.py`, `test_scoring.py`, `test_access_control.py`, `test_users.py`, `test_users_boundaries.py`, `test_approval.py`, `test_m4_boundaries.py`, `test_dashboard.py`, `test_auth_lock_boundary.py` |
| Interface (frontend) | `validation.js`, `api.js`, `format.js`, React components | `node:test`. Pure modules (`validation.js`, `api.js` with a mocked `fetch`, `format.js`) are unit tested. Components are render tests: esbuild bundles the component and `react-dom/server` renders it to HTML. Browser behaviour (focus, layout at 375px, clicks) has no automated test because there is no browser automation; the checklist in `docs/ui.md` describes those checks, with results pending until a tester records them | `validation.test.js`, `api.test.js`, `format.test.js`, `scorecard.render.test.js`, `notfound.render.test.js`, `roles.render.test.js`, `review.test.js` |

**Risk.** The product helps a loan officer decide on a real person's credit, so the costliest failures are a wrong score or label, a wrong flag (BR3), a rule applied on the wrong side of a threshold, and data saved from an invalid form. That is why the scoring and validation code is tested on both sides of every boundary, and why every rejected request is checked for an unchanged record count. Access control and secret handling are tested because a leak of personal data cannot be undone. The weakest layer is the visual layout: it still needs the recorded manual browser check.
